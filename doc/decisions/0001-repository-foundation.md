# 0001: 設計の取り込みとリポジトリ基盤

- 日付: 2026-09-06
- 状態: 採用
- 元設計: `nepl3-design-2026-09-06-r1`

## 問題

元の資料は設計・実装依頼・設計時の検査報告をまとめたものです。設計の完成、Rust実装の完成、現在実行した検査が混同されると、後続の開発で未実装の機能や未実行の受入試験を成功扱いする危険があります。また、ユーザーが指定した正式な文書配置は `doc/` です。

## 判断

1. 文章仕様を `doc/spec/` へ移し、正式な入口を `doc/README.md` とします。機械可読の `design/`、`interfaces/`、文法source、例、受入入力は責務ごとに維持します。ローカルの `.tmp/` は除外します。
2. 元manifestと設計検査報告は `doc/history/` に元byte列で保存します。移設後の検査結果へ読み替えません。
3. `design/tasks.json` はタスク定義に専念し、実行状態を `implementation-status.json` へ分離します。タスク本文と索引は開発toolsで生成・差分検査します。
4. 18 crateの依存表は目標構成とし、Cargo workspaceには実装済みのmemberだけを登録します。基盤整備段階では開発toolsを実装し、言語crateの空実装や成功stubを作りません。
5. CIは現存する実装を3つのnative OSで検査します。mainの同じ検査済みSHAからsource archiveを配布します。WASI・ブラウザ・別process providerの受入条件は実装とrunnerがそろうまで未実行です。
6. メインagentが統括し、実装subagentと独立レビューsubagentを分けます。設計に矛盾が見つかった場合は、根拠と影響範囲を確認して仕様・schema・例・受入条件を同時に訂正します。

## 影響と確認

仕様の意味を縮小せず、現在の実装と将来の目標を区別します。metadataからのファイル参照、タスクID・依存・受入条件参照、workspace依存とDAG、生成タスクの整合を開発toolsで検査します。一般のMarkdownリンクは別途レビューします。取り込み元で報告された43項目の検査と37群のruntime受入条件は別物として保持します。

この判断は元設計全体の正しさを承認するものではありません。個々の実装に入る際にも、関連する契約・文法・不変条件を独立レビューし、矛盾や不足を記録します。
