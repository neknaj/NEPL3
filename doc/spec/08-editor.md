# 08. 共通editor serviceと診断

## 方針

一度宣言したgrammar/binding/style情報からeditor機能を導出する。専用parserも同じfactsを返して支援を受ける。共通分類をプログラミング言語の要素に限定しない。

## 1. AnalysisSnapshot

入力はSourceSnapshot集合、profile/package revision集合、明示的なresource/schema環境、解析options。結果はParsed tree、内部views、Scope/Entity/Occurrence、typed Relations、Diagnostics、ExpectedAt、Dependencies。

全結果にSnapshotIdとanalysis keyを付ける。keyには言語/reader/providerのrevision、context、操作optionsを含む。spanのある結果を意味値だけのcacheから再利用しない。

Binding の prepared request は AnalysisKey の treeDigest、profileDigest、executionDigest、requestDigest を固定する。treeDigest は局所nodeを正準化した完全な ParseTree の NDF/1 CBORに基づき、明示sourceのidentity・URI・元bytes、payload、環境、各選択contextを含む。profileDigest は解決済みProfileの意味identityで、選択schema、provider実装、resource、既定limitsを含む。executionDigest はalias名順の実package execution identity表に基づき、同じ意味でも異なるarena配置を区別する。requestDigest はanalysis ID、型付きBindingOptions、有効な操作Limitsを含む。現在のBindingOptionsは空recordであり、未実装の意味optionを黙って受け入れない。

treeDigest・executionDigest・requestDigestは `SHA-256(domain || canonical NDF/1 CBOR(value))` とし、tree・execution・requestのdomainはそれぞれ `nepl3.analysis.tree/1`、`nepl3.analysis.execution/1`、`nepl3.analysis.request/1` に終端zero byteを付ける。profileDigestは既存の解決済みProfile identityアルゴリズムに従う。codecは正準化とhashのWork・割当・出力量を操作Budgetへ計上する。SourceSnapshotを内包した値のhash計算だけで新たなsource lookup権限を付与しない。

prepareは明示的に渡されたBudgetとSourceAdmissionで要求を検査し、keyを算出する。実行LimitsはProfileの上限を超えられず、executeのBudgetのLimitsは要求と完全一致しなければならない。prepareと実行は独立した操作予算を使うことも、同一pipelineの累積Budget/SourceAdmissionを共有することもできるが、使用済み量を払い戻さない。keyは有効上限を保持し、開始時の残量やtransportの観測Usageを認証する値ではない。途中停止結果から完了proofを生成しない。

初回BindingRequest decoderは元のRust要求を持たず、明示sourceを持つ受信treeと選択済みProfileからkeyを再計算する。自己申告keyやLimitsを通信認証・hostの実行許可へ昇格しない。受信raw要求のprepareでも再計算・一致検査を行い、その間に変更されたtree/contextや条件を拒否する。BoundBindingReplyは全結果枝のkeyと通常BindingReplyを保持する。raw返信decoderの一致検査は意味proofの発行ではなく、完了proofは実BindingPlanの実行からのみ得る。

BoundBindingReply.for_source はhostが現在要求しているAnalysisKeyとの完全一致とSourceRefのrevision/digestを検査してから、完了したBindingAnalysisを公開する。これは定義・参照検索の前提となる照合入口であり、positionからの対象選択、定義ジャンプ、参照検索、renameのアルゴリズム完成を意味しない。既存のunkeyed analyzeのFactSet.analysis_idだけを、editor用のstale判定として使わない。

## 2. 自動で得られる機能

schemaのform/leaf/fieldとreader captureから構文ハイライト、構造的selection、expected categoryの補完を提供する。binding/reference/export/importから定義ジャンプ、参照検索、未定義/重複診断、scope内の候補補完を提供する。name fieldとenclosing rangeからoutlineを作る。ドキュメントfieldを宣言すればhoverに出す。

型推論、回路幅、数値計算結果等はdomain factsの追加で精度を上げる。grammarだけから任意domainの意味を推測したと主張しない。

手書きreaderにはview/factsの同じcontractを要求する。内部viewなしならtoken全体のfallbackだけ。すべてのcustom readerへ精密な内部支援を自動生成できるとはしない。

## 3. regionの選択

source positionから、同一snapshot上で包含する最小のfield/elementを選ぶ。grammar priority、最内側、宣言順でtie-breakを固定する。sentence内のreadingを問い合わせたらsentence token全体よりreading viewを優先する。

highlightは内部regionへ分割し、leafに近い具体的classを優先する。overlapを持つ元データは保存するが、LSPへは非重複・source順・単一行に正規化したspan列を返す。色はthemeに委ねる。

## 4. definitionとrelations

現在のkeyed queryは、完了したBoundBindingReplyとQueryRequest(key, SourceRef, byte offset, kind)を受ける。SourceRefのrevision/digestと現在要求するkeyを照合し、UTF-8 scalar境界を検査する。範囲は半開区間で、終端byteや空白を直前の名前へ吸着させない。包含するOccurrence.spanのうち最小のものを選び、同長なら確定factsの発行順を使う。これは名前Occurrenceに基づく選択であり、3節のfield/view/grammar priorityを含む一般region selectorは後続実装として残る。

QuerySelectionは元のOccurrenceId・span・確定ReferenceResolutionとopenInputを保持する。対象なしはNone、未解決とOpen namespaceのfree inputはopenInputで区別し、DeferredもUnresolvedに潰さない。定義候補は確定resolutionのEntity ID列に従い、曖昧な全候補とその順序を維持する。位置を持たないEntityはIDとlocation=Noneを返し、仮のsource位置を作らない。locationがある場合はURI、定義全体range、任意の名前selectionを分離する。

Referencesは選択した各Entity IDごとに確定Occurrenceを検索する。既定ではResolvedのReferenceだけを返す。ReferenceOptionsはDefinition・Import・Export role、およびそのEntityをAmbiguous候補に含むOccurrenceをそれぞれ明示的に追加できる。曖昧な出現はambiguous=trueで区別し、同綴りの別Entityを混ぜない。通常BindingのImportが子のexport候補を可視にする操作と、providerが明示的に返すImport roleのOccurrenceは別であり、queryが新しいOccurrenceを捏造しない。Customの更新後も元stageから名前検索をやり直さず、確定resolutionを用いる。

QueryReplyはDefinition/References/Invalid/StoppedとReport、参照位置に必要な宣言sourcesを持つ。現queryは新たな診断・eventを発行せず、解析診断は元BindingReplyに残す。query失敗はtyped原因または元StopReasonを保持し、候補途中列を成功結果として公開しない。使用済みBudgetとSourceAdmissionは払い戻さない。sourcesはsource ID・revision・digest順に正準化する。

QueryRequestの初回decoderは元Rust要求を必要としないが、自己申告keyから完了したBindingAnalysisを作らない。実queryはhostが保持する同keyの意味proofを使う。返信decoderは対応する要求、role options、候補ID列、範囲・URIと明示source閉包を検査し、ambient sourceで欠損を埋めない。これはraw結果の構造検査であり、通信認証やリモートの解決結果の意味証明ではない。

Customを使うprepared実行にも同じkey/有効Limitsの検査を適用する。hostのauthorizeが参照する設定・権限方針・明示resourceを変えて結果が変わる場合、hostはその入力変更をProfile resourcesやschemaで宣言したrequest options等のidentityへ反映し、旧keyの結果を再利用してはならない。keyは実行時FactAuthorityそのものを認証せず、同じkeyのまま任意のhost設定変更を安全に許す値でもない。

definition結果はoriginSelection、targetUri、targetRange、targetSelectionを分離する。entityのnameだけ選択しつつ定義全体も示せる。sourceが配布packageの場合は読み取り専用virtual documentとして公開できる。

CorrespondsToには「対応文へ移動」、Originには「生成元へ移動」を提供し、通常の定義ジャンプとは別relationとして扱う。多義的な解決は複数候補を返し、単語一致で一つに決めない。

renameは同じEntityを指すOccurrenceだけを対象にする。新名の適格性、予約語、shadowing、scope内衝突、外側の参照の捕捉まで再検査する。SourceMapの逆変換が一意でない場所はRenameNotInvertible。全TextEditはrevision付きでatomicに返す。

現在の rename は `RenameRequest(key, source, offset, newName, writable)` に対する二段操作である。対象選択は上記の名前Occurrence規則を使う。writable はhostが許可した元snapshot集合であり、受信したSourceRefやURIだけから編集権限を発行しない。未選択・未解決・曖昧・Deferred・位置なしを型付きで区別して拒否する。予約headは対象EntityのFactNamespace.schemaを所有する選択済みpackageのForm.spellingと照合する。別schemaの言語だけに存在するheadを予約語へ加えない。最終的な名前のreader適格性と構文選択は実再parseで検査する。

prepareは元の実parse完了結果と、その同じimmutable treeを借用するprepared Binding要求、同keyの完了解析を要求する。private RenameDraftには元revisionへの編集候補と候補snapshot集合を保持するが、成功transactionや編集列の公開入口を与えない。draftはrename操作専用SourceAdmissionを所有し、同じ有効LimitsのBudgetをprepare・再parse・再解析・acceptの間、排他的に借用する。失敗やdraft破棄で使用済み費用を払い戻さない。別候補は同じ元revisionから分岐でき、共有の元SourceStoreを候補作成時に変更しない。

逆写像は宣言SourceMapを全探索し、同一source・revision・digest上の一意な連続範囲へ達するExact対応だけを使う。隣接するExact区間は同じbyte変位で穴なく全対象範囲を被覆するなら結合でき、表順や区間分割で結果を変えない。異なるsourceや変位への多義性、被覆穴、Transformed、Composite/Synthetic origin、cycleは拒否する。quoteやescapeから復号された意味名と元bytesが異なる場合、明示逆encoderがないままquoteを消す置換を行わない。探索・範囲比較・複製はWork/Depth/Nodes/Allocationの対象となる。

元への編集からExact対応を前向きにも適用し、影響する派生snapshotの次revisionと内部編集を作る。派生側の未対応byteは保存する。再parseが返す全宣言sourceはdraftの指定snapshot集合と、ID・revision・digest・URI・全bytesで一致しなければならない。mapのtargetであることはsnapshot全体の照合免除にならない。hostがreaderの生成sourceを予約する場合も、この候補identityを使う。公開する編集は許可された元snapshotへの列だけで、派生側の内部編集を追加の書込権限として外部へ渡さない。

acceptは候補の実parse完了結果と同じimmutable treeに対するprepared要求・完了解析を照合する。Profileの意味identity、provider/package実行identity、options・analysis ID・有効Limitsを維持し、候補全source、構文kind/field/選択context、編集に対応する位置と意味payloadを検査する。Entityの対応は宣言位置・scope/namespace・意味名に基づき、opaque IDの数値一致だけで決めない。対象外の名前も含め、Resolved・全Ambiguous候補・Unresolved/free input・Deferred・Customの確定resolutionが対応していることを検査する。後続scopeで名前検索をやり直してCustomの判断を上書きしない。衝突・捕捉・構文変更・別要求との組替え・停止では編集列を一部も公開しない。

nativeのCompletedParseは実ParseSessionのread/resume/reserve/resume_headがCompleteを返した場合だけ発行する所有proofであり、待機・回復・停止は通常のParseReplyを保持する。元と候補のprepared treeがこのproofの同一immutable treeを借用する条件はnative内部の保証で、pointerやRust ABIを公開schemaへ露出しない。raw treeの取出しはproofを消費し、raw ParseTreeやNDF decodeから再発行できない。将来の別言語・別process parserも、認証された発行要求と実parse実行結果を結ぶ同等のhost境界を必要とする。現在のraw rename request/reply codecはschema、要求key、書込対象、old digest、編集非重複、元source閉包を検査するが、通信認証やparse実行証明を発行しない。

RenameReplyのCompleteは新AnalysisKeyと全TextEdit、Invalid/Stoppedは編集なしを返す。Reportは実消費Usageを保持し、この操作自身は新規diagnostic/eventを発行しない。再parse/解析の正式Reportはそれぞれの返り値に保持する。受信したUsageの内部整合と外部処理費用の認証は別の責務である。最終適用は呼出側の元SourceStoreに対し、base revision・old digest付きのatomic applyで行う。一般region selector、任意encoderによる意味名の逆変換、増分再解析、外部parser実行の認証transportはこの段階の完成範囲に含めない。

## 5. 不完全入力

構文エラーで文書全体を失わない。treeにMissing(expected, anchor)、Unexpected(span)、Unparsed(range,reason)を持てる。通常の成功nodeと区別し、checked値へ混入させない。

EOFで既知arityの子が不足するとMissingを作る。現在のcategoryに不適合だがancestorの明示的同期位置に適合するtokenは消費せずMissingを挿入できる。同期根拠がなければUnexpectedとして消費するか、その範囲をUnparsedとして残す。どちらを選ぶかはpackageのRecoveryPlanに固定する。

arity不明のheadの子の数を推測しない。該当rangeをUnparsedにし、既に確定した周辺の情報だけを返す。prefix構文では誤り後の正しい境界が入力だけから復元できない場合がある。完全に復元できると広告しない。

SentenceLiteralでは改行/EOF/終了引用符が回復境界。注釈の不足括弧についてexpected tokenと開始位置を返す。期待する閉じ括弧を自動挿入するfixは提案であり、ユーザー操作なしにソースを書き換えない。

## 6. 増分解析と取消し

編集はbaseRevision付きTextEdit列。編集後に新snapshotを作り、古いsnapshotは不変。編集に交差しないrangeは編集写像で新snapshotへ明示的に移せる。交差するtoken、子contextを変更する前方宣言、その依存下流を無効化する。

再利用可能なnodeは、source内容、entry category、reader/context/provider digestが一致する場合に限る。独立な埋め込みや意味値は再利用できる。全再解析との出力比較をconformanceに含める。最悪時の全体再解析は正しい経路として残し、常に編集差分だけの計算量を保証しない。

LSP側はdebounceとcancelを担当する。coreは明示的budget/pollを使う。古いrevisionの結果は公開しない。cacheと統計は明示的session stateであり、隠れたglobalにはしない。

## 7. LSP adapter

3.17で定義された位置encoding/diagnostic/semantic token/definition等の契約を利用し、機能はcapabilityで交渉する。UTF-8/UTF-16/UTF-32の位置変換をLineIndexで行う。UTF-16をfallbackとして必ず扱う。日本語や補助平面文字のbyte数、UTF-16 code unit数、表示幅を混同しない。

一般的なDSL class名はsemantic token legendの独自typeとして出せる。クライアントが対応しない場合は表示fallbackを使うが、NEPL3内部kindを書き換えない。position/legendの変換はdomain crateに置かない。

nepl3-lspは一つの汎用server。workspace設定から拡張子とLanguagePackageを選択し、各DSLごとのserverの再実装は不要。VS Code/Neovimには接続と設定だけの薄いadapterを置く。packageを変更したらanalysisを無効化し、必要ならlegend登録も更新する。

## 8. 診断・ログの表示

同一DiagnosticをCLI、LSP、browserへrenderする。CLI stderrは表示adapter、stdoutは要求された成果物だけ。JSON/NDF診断出力と人間用表示を分離する。詳細traceは明示的に選択し、ソース全文や環境の機密値を既定では記録しない。

情報が不足する場合はstage/requirementsとして表示し、存在しないsource位置を作らない。providerの内部エラーとユーザーの構文ミスを区別する。

## 9. workspace trust

通常の解析と診断で対象プログラムをevaluateしない。Grammar reader providerはhostのallowlist・署名・schemaで制限する。workspaceからnative pluginを自動build/loadしない。untrusted providerには隔離runnerが必要で、ない環境ではTrustRequiredを返す。巨大入力/再帰/イベント/出力にも上限を設定する。
